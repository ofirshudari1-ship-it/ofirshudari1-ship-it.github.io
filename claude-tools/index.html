Skills and Agents for Claude Code

Five custom skills and four custom subagents, built while maintaining several software tools in parallel. They were not planned up front: each appeared after the same manual check had repeated three or four times. Free, no account, open source.

Download everything (ZIP) View on GitHub

Skills

  • release-checklist

    Skill

    Runs a release check before every build. It confirms the version number is in sync everywhere it must appear (version file, installer file name, About screen, changelog), that the installer was actually rebuilt rather than left as a stale copy, and that the project folder is free of build leftovers. For electron-builder tools it also verifies that the update feed files (latest.yml, .blockmap) were really uploaded, not just the .exe, because without them the update check silently breaks. If the specific tool has its own checklist it follows that; otherwise it falls back to global sync rules.

    Triggers on: "Ready to release", "check before release", "new version", "before I ship the installer"

    View file

  • grep-audit-callers

    Skill

    Before changing a shared function, module or API, it first maps every caller across the whole project tree (not just the file with the definition), classifies each one (no change needed / needs update / dead code), and reports the full list before any code is touched. This method exposed 3 real bugs in 3 separate rounds on a real project; it is not a theoretical technique.

    Triggers on: "change a function", "refactor", "who calls this function", "change a shared API"

    View file

  • secrets-hygiene-check

    Skill

    A zero-secrets check before a commit or release. It scans the source (excluding node_modules/dist/build) for common patterns of API keys, tokens, passwords and database connection strings, confirms .gitignore covers environment and credential files, and checks that configuration is really loaded from environment variables instead of hard-coded. Every finding must cite a real file and line; anything uncertain is flagged for manual review rather than stated as fact.

    Triggers on: "check secrets", "before commit", "possible key leak", "security check before release"

    View file

  • daily-project-brief

    Skill

    A short status brief across every tool in a working folder that holds several projects: what is stuck, what is stale, what needs attention, in 5-7 focused lines and without a full audit. It is based on a central status document plus each tool's version and changelog files. When something needs a deeper look, it points to a separate audit agent instead of doing the audit itself.

    Triggers on: "project status", "daily brief", "what is stuck", "status of all tools"

    View file

  • system-upgrade

    Skill

    The biggest of them all. An end-to-end upgrade process for an existing web app, Electron app or Chrome extension. It scores the system on 10 dimensions (RTL/Hebrew, responsiveness, WCAG 2.2 accessibility, design quality, UX and states, forms, perceived performance, ease of setup, AI layer, and UI code health) using a deterministic detection script plus live browser testing, not just code reading. It produces a before/after report and a sprint plan with measurable goals, executes it with a commit and screenshots per sprint, and hands the result to a separate, skeptical evaluator (see the upgrade-evaluator agent below) rather than checking its own work. It includes background material for each of the 10 dimensions and ready-made report and plan templates.

    Triggers on: "upgrade the system", "the system is a mess", "fix RTL/mobile", "audit UX"

    View folder

  • local-designer

    Skill

    A global, project-independent designer skill that produces marketing assets entirely locally: composed SVG/HTML rendered with sharp and headless Chrome, with no paid generative API and no per-image cost. It reads brand identity (colors, font, logo) from the project files first. Only if that is missing, and only if the brand already exists in Bloom, it may pull the brand profile from there, read-only (get_brand/list_brands), without generating images or spending credits. It never calls a Bloom tool that generates or edits images.

    Triggers on: "design this for me", "create an image/banner/post/story", "compress images", "check the brand colors of [business]"

    View file

Agents

  • system-upgrader

    Agent

    The executing half of the system-upgrade process (it loads that skill). It scans an existing system and upgrades it end to end: RTL/Hebrew, mobile and desktop, accessibility, non-generic design, UX/states/forms, ease of setup and the AI layer. It runs the deterministic check and a live browser check, prioritizes findings, and fixes them in sprints with a commit and before/after screenshots. It always runs together with upgrade-evaluator; an agent never evaluates its own upgrade.

    View file

  • upgrade-evaluator

    Agent

    A separate, skeptical evaluator for system-upgrader's results. It runs in a clean context without seeing the reasoning of the agent that did the upgrade (which is exactly the point: a model grading its own work tends to score too high). It reads the plan and the report, re-runs the deterministic check, opens the live app in a browser, verifies every sprint goal in practice, and scores each of the 10 dimensions from 1 to 10 with evidence. Fully read-only; it never touches code.

    View file

  • page-upgrader

    Agent

    Like system-upgrader, but focused on a single page or module (for example /calendar or /settings) rather than a whole app. It adds a dedicated research step, working out what a page of this type should contain at all, before identifying what is missing. It then upgrades design and UX separately for mobile and desktop, and confirms that tsc, eslint and the build pass before committing. It also loads the system-upgrade skill for the base rules.

    View file

  • tool-standards-audit

    Agent

    Runs a full audit of one tool from a working folder that holds several projects, against a central standards document. It checks the code as it is now (it does not copy claims from an earlier audit without re-verifying them), including root cleanliness, version sync, zero secrets, RTL/i18n, install language and location, single-instance behavior, DPI, and clean uninstall. Every line in the report must cite a real file and line; a question mark is better than a guess. It updates the tool's audit file and the shared status table.

    View file

How to install

Copy the file (or the whole folder, for system-upgrade) into your Claude Code configuration folder:

~/.claude/skills/<name>/       # available in every project
~/.claude/agents/<name>.md      # available in every project

Or, to make it available in one specific project only:

<project>/.claude/skills/<name>/
<project>/.claude/agents/<name>.md

No build and no package installs: they are plain Markdown files (plus one dependency-free Python script inside system-upgrade).

Note: three of these (release-checklist, daily-project-brief and tool-standards-audit) were originally written against a specific personal folder layout. The mechanism itself (version-sync checks, mapping callers before editing, refusing to grade your own upgrade) is general and useful in any project; the path names in those three are working examples, not hard dependencies.
